CLI/skills system). Read alongside `build-questions.md`. This file is a reference, not a plan —
stay neutral when using it; every "build implications" line is a constraint the plan must satisfy,
not a design recommendation.

## 2. Do not reopen

Per the operator's private notes for this handoff:

| Decision(s) | What stays fixed | Operator's stated reason |
|---|---|---|
| D13 / D24 | Approve is a press-and-hold button. No Touch ID or Face ID step. | D13: approving posts nothing (it's reversible before the real post), so the hold is a sufficient failsafe against accidental taps. D24: kept even after the 24 Sep review flagged that an agent with computer-use/browser tools could press-and-hold it too — the operator's answer is that **the build must stop agents from reaching the button or its call**, not that the button gains a biometric step (`ui-direction.md`:34). |
| D31 | The Cortex chat stays (ships, isn't deferred). | Operator kept it directly against the 24 Sep product review's recommendation to defer Cortex until experiments run (`ui-review-2026-09-24.md` D.6). Only *build order* — phone before Mac — is still open for confirmation, not whether Cortex ships. |

A strategy that reopens "should Approve require biometrics" or "should Cortex be cut/deferred" is answering a question the operator has already closed. The open problem attached to D24 is narrower: **how does the build technically prevent an agent from triggering the existing button**, not whether to change the button.

## 3. Invariants the build can never break

These come from `AGENTS.md` §"What the loop may never change" plus the mechanisms that currently enforce them. A UI is a new caller into this system — it inherits every one of these, it does not get to relax any of them because the interface changed.

| Invariant | MUST / MUST NOT | Source |
|---|---|---|
| No X writes: never post, schedule, or call an X write API. | MUST NOT let the UI (or any agent it drives) call a write endpoint. The only proven guarantee is that the Keychain keys are Read-scoped and X itself refuses writes from them. | `AGENTS.md`:13; `reference/x-api.md` P1 (verified: every tested response carried `x-access-level: read`) |
| Only the operator approves. Today the one path is the typed `/approve <slug>` hook, which writes `APPROVED`. | MUST NOT let any agent, script or scheduled job approve. `AGENTS.md:14` currently allows only the typed command, so the hold button (D2, D13) needs the operator to change that rule first, with an operator-only path at least as strong as the typed one that nothing an agent can reach may call (D24 open problem, §2 above). The typed `/approve` stays as backup. | `AGENTS.md`:14; `.claude/hooks/approve.py` (UserPromptSubmit hook, matches literal `/approve <slug>` typed by a person, lines 18, 39) |
| Loop state (`loop/state.json`, `ledger/*.json`, generated `experiments.md`/`learnings.md`/`ledger/SUMMARY.md`) changes only through `scripts/loop.py`. | MUST NOT let the UI or any agent it drives write these paths directly, including through a "convenient" API layer that skips `loop.py`. | `AGENTS.md`:16; `.claude/hooks/guard_approved.py` `LOOP_STATE` regex, lines 34–35, 86–87 |
| Truth budget: every figure sourced this session — an official page, `PATHS.md`/`CLAIMS.md`, or the operator. | MUST NOT let Cortex, a draft, or any UI-generated summary state a number (dB, %, $) that isn't traceable to one of those three sources in that session. | `voice/exit-zero.md`:41–43 |
| Fail-closed fact-checks. | MUST make any new automated check (a UI-side "quick check" of a draft, a Cortex claim) fail closed — refuse/flag rather than silently pass — matching how `.claude/skills/verify-settings` and `approve.py`'s own exception handling behave (`approve.py`:70–77: any exception blocks and approves nothing). | `AGENTS.md`:18–20; `.claude/skills/verify-settings` ("Fail closed" in its description); `.claude/hooks/approve.py`:70–77 |
| The shared gate refusals (`scripts/post_thread.py`). | MUST run the *real* gate logic (or call the real script) before anything is marked postable in the UI — not a reimplementation that can drift. The 25 Sep review's #3 Must-fix finding was exactly this: the mock's "final checks" accepted `reply with`, >600 chars, missing PAID→FREE header, and empty cards. | `AGENTS.md`:51; `ui-review-2026-09-25.md` finding #3 |
| Keys never enter a session. | MUST NOT let any UI backend, agent, or log read Keychain values directly; only `scripts/x_api.py`, in its own process, may. MUST NOT let a shell tool run `security find-generic-password`/`dump-keychain` against this service — the existing hook already denies this pattern for CLI sessions and any new execution surface needs the equivalent. | `reference/x-api.md`:5; `AGENTS.md`:13; `.claude/hooks/guard_approved.py` `SHELL_KEYCHAIN`, lines 36, 79–81 |
| No hand-editing of drafts' approval marker or nested approval via spawning another agent to type it. | MUST preserve (or re-implement at the new execution layer) the two guard patterns: direct writes to a path named `APPROVED`, and shelling out to `grok`/`claude`/`codex` with a prompt starting `/approve`. | `.claude/hooks/guard_approved.py` `SHELL_MARKER_WRITE`/`SHELL_NESTED_APPROVE`, lines 37–44; `MARKER`/`APPROVE_CMD` construction (deliberately split strings, lines 23–24) obfuscates the literal from casual grep — a hint that the guard itself expects to be probed |
